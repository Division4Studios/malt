# Current status

This page maps what MALT does today against the road to 1.0. It is accurate as of main
[`0de06b6`](https://github.com/Division4Studios/malt/commit/0de06b6) on 2026-10-19. The scope, order and exit criteria
for 1.0 live in the roadmap issue [#263](https://github.com/Division4Studios/malt/issues/263) and the
[v1.0 milestone](https://github.com/Division4Studios/malt/milestone/1). When this page and the live issues disagree, the
issues win.

MALT is pre-1.0. No version has been tagged or released.

## How to read this page

- **Merged** means the code and its tests are on main, and the issue was closed with an evidence comment naming the PRs,
  source files and tests.
- **Merged, issue open** means the code is on main but the issue is still open, usually for closure or a verification
  clause.
- **Partial** means part of the scope is on main and a named part is missing.
- **Remaining** means the work has not started or needs a person.

Most regression tests use fixtures for model inference and GitHub. Local Git, worktrees, SQLite, validation commands and
the loopback broker and console are real. A source merge does not upgrade a running broker: restart it deliberately (see
[operating MALT on itself](operating-malt-on-itself.md)).

## Evidence and its limits

- No paid model turn has exercised a liveness extension, a checkpoint decision, a Copilot assignment or a Codex Cloud
  task. Fixture and fake-clock tests cover those paths.
- No protected-branch delivery with distinct reviewer identities has run end to end
  ([#259](https://github.com/Division4Studios/malt/issues/259)).
- The service-worker lifecycle, the `no-store` API boundary and the offline status are covered by automated tests, not
  by an installed browser ([#261](https://github.com/Division4Studios/malt/issues/261)).
- The backend has three exactly pinned runtime packages (`@modelcontextprotocol/sdk` 1.32.1, `zod` 4.6.7 and
  `node-pty` 1.2.0-beta.15) and needs Node.js 24.15 or newer. The browser has no production dependencies. See the
  [dependency policy](dependency-policy.md).

## Keeping the board honest

1. Close an issue only when its code is on main and its evidence comment names the PRs, source files and tests.
2. When part of an issue is proven, check those criteria and keep the remaining scope open.
3. When an open prerequisite blocks an issue, link the prerequisite instead of starting the work.
4. Treat old "blocked" comments as history, not as proof that a defect still exists.
5. Never invent a QA approval, force a local ledger to Done, or claim a running broker was redeployed.
